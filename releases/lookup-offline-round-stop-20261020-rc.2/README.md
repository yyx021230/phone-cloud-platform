## 用户要求与实现

- **业务查询中手机掉线**：连续30秒设备离线或Agent心跳失效，事务隔离原手机执行；原客户lookupId、手机号、幂等键及别名不变，未完成号码重新排队，分配其他已经探测正常的在线手机。不是取消客户查询，也不停止整轮。没有可用手机就等待；已受理任务原60分钟总预算不延长，跨机不再受已消耗的首次30分钟排队期限误伤。
- **调用结束接口**：明确终止本轮，停止派发和探测、取消未完成工作、保留完成结果。持续离线手机隔离后不再阻塞stopped或下一轮prepare。不会在用户要求停止后又跨机继续查询。
- **自然结束**：有排队/查询/跨机等待业务不算空闲；业务完成后连续空闲15分钟才自动结束。之前业务留下的离线隔离手机不参与新一轮停止门槛。
- **恢复连接**：旧设备继续保留物理占用和代次，先真实stop/ACK清理，再释放和重新探测；不能凭离线计时宣称设备已经停止。终态作业的payload/ACK/迟到结果被现有门禁拒绝，客户查询仅接受当前尝试结果。

延续主文档7.15.13/rc.1的停止解耦，明确扩展正常业务的掉线跨机路径，替换旧“未知执行只能一直等待原设备”的限制，仅对确证持续离线且旧作业撤销持久化成功生效。在线unknown不自动跨机；落库/代次绑定失败保留原任务，不提前新派。正常查询没有重复提交，故障重试可能在另一设备重新执行同一号码；网络分区期间不能证明旧物理操作从未发生，不能宣称设备物理执行exactly-once。

## 代码、兼容与范围

三个云文件：managed-lookup调度状态、platform adapter的离线判断和旧尝试撤销、round-stop忽略既有跨机清理通道。三个可选JSON字段offlineHandoffSince/offlineHandoffAt/offlineHandoffRequestId；复用原请求排除设备与总预算，无SQL迁移。四外部接口/请求/响应/单API Key均不变，七份说明/OpenAPI与原HTTP下载包同步。

候选从rc.1递归组装，包含尚未上线的待命容量收敛和卡片状态候选；旧标签不移动。生产基线为前轮核对的lookup-idle-refresh-20261020-deployed.1，本轮零生产连接，不能把旧读数当本轮线上核验。根仓旧业务及已有改动未动。

没有修改或操作Agent、ADB、SYSTEM、授权密钥、驱动、USB、媒体、投屏和控制路径。192冻结文件核验保留。未安装依赖；仅使用现有本地node_modules和独立loopback Postgres。
