# 企微 CPS 手机号接入上线准备

日期 2026-11-09。基于合并候选 `wecom-add-wechat-merge-20261106-rc.1`（`aefdbe4`）。本次复核候选增加接口回归和发布材料，CPS、主平台和 Windows Agent 的运行代码与合并候选一致。正式部署另核对实际运行基线。主分支和整个候选树不能作为生产覆盖包。

## 对接方确认

- 设备查询与客户下发共用平台基础地址，路径分别为 `POST /api/v1/lead/devices/query` 和 `POST /api/v1/lead/dispatch`。若双方确认采用现有公网 HTTP 入口，按示例只在现有业务站点接入这两个精确路径。当前协议约定 HTTPS，公网地址和协议待双方确认。CPS 的正式 HTTPS 回调地址单独提供。
- 本次接入的成员配置使用 `wecom_phone`、`wecom_name`、`deviceNumber`、`appSlot=main` 及启用、核验标记。正式配置采用纯手机号映射，成员条目不配置历史企业和成员 ID，确保查设备回包省略这两个字段。被添加的客户 `phone` 无须预先加入名单。
- 用安全渠道注入正式接入凭据和回调。已受理的线索重试使用原业务字段与 `lead_id`，每次重新签名。CPS 以 HTTP 2xx 且响应体 `success=true, code=200` 确认收到回调。

## 发布前核对

1. 从真实生产宿主的 `ACTIVE_PLATFORM_RELEASE.json` 核对运行及下次启动镜像、容器热补、Compose 和文件哈希。以运行代码确认两个内部设备查询、企微任务提交和原任务查询可用，Windows Agent 已对拟启用的手机声明备注手机号核验能力。仓库历史企微回执可供比对。若运行基线或原生执行器缺少必要能力，先单独收敛补丁、回归和维护范围，避免将不同版本的共享代码一并带入。
2. 备份有效 Nginx 业务站点配置、独立 CPS 进程配置和账本，记录原平台镜像、Agent 文件哈希、活动占用和已有企微发送记录。生产 CPS 使用独立 PostgreSQL 账本，先确认 schema v2、稳定的 state key 和独占协调锁。已有发送记录及未知结果需要先对账再接单。只有经核对的备份和回滚点才能用于切换。
3. 仅启独立 CPS bridge，固定绑定 `127.0.0.1:8797` 或经核对的回环端口，并使用正式平台的安全上游。先用隔离预览配置做连通和签名查设备。预览账本与正式发送账本分别配置，正式账本保留稳定命名空间和原防重记录。正式邀请与回传需要用户授权的线索和空闲测试设备。
4. 将 [精确路由示例](nginx-location.conf.example) 合入现有业务站点前，按项目 Nginx 隔离流程验证有效配置、五类临时目录和原站点路由。仅在获准窗口加载。D-075 在真实媒体宿主机发布前后执行只读 `verify --live`，检查失败停在当前步骤。该片段本轮仅作本地静态核对。
5. 先做签名查设备，核对实际 JSON 中两项历史 ID 均缺席。随后单机、双机灰度正式流程，核对账号、回调确认、重复下发和查名占用。发布前后对比查名接单、已有会话和设备锁，再决定是否扩大范围。

## 回滚

先暂停新 CPS 下发，盘点已受理线索、发送结果和待回传记录。撤回本次两条 Nginx 路由或恢复已备份配置，按相同隔离要求核验后加载。独立 CPS 服务按受理及回传状态排空或停在原记录上，保留 PostgreSQL 账本、state key、发送凭据和回传记录。回滚后检查原查名入口和活动会话。主平台、Agent、ADB、Windows 和媒体服务均沿用发布前状态。

## 本轮证据

见 [验收回执](verification.json)。本机已有联调服务仅发出签名设备查询。下发、执行结果、回传和查名占用在隔离的本机 HTTP 环境验证。Windows 原生和正式公网验收待发布窗口，线上未改动。
