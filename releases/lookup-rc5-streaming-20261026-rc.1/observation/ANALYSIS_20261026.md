## 一、服务器为什么崩溃

**已确认是全机内存耗尽引起内核OOM杀进程，自动重启反复进入大状态加载/保存路径，放大故障。**

内核记录北京时间09:48:32、09:49:55、09:51:30、09:52:57、09:54:33、09:56:01六次杀掉旧生产Node进程，匿名RSS约2.58–2.72GiB。10:05:04第一次仅优化写入的恢复候选也被OOM杀掉；不能把这第七次算成旧版。宿主机约7.1GiB内存、4核，无swap。

完整状态实际解压530,660,465字节；Windows任务与自动化任务重复事件负载占约449MB。旧路径完整JSON读取、解析、多个结构化表并行覆盖，再整包编码写入；Node与Postgres后端的大内存峰值叠加。旧生产在本次rc.5激活前已发生异常，不能归因于新功能版本已启动。最初触发峰值的是哪一条业务写入、用户所见90% CPU具体由哪个进程占用，没有足够历史采样，仍未证实。

当前组合已包含双向流式加载/保存及串行覆盖修复。11:07左右Node RSS约974MiB、宿主可用约3.3GiB，容器重启0、OOM=false；两秒CPU短采样38.9%、iowait0.4%，healthz/readyz均200。近期有界日志未发现新的持久化/调度/AI/OOM关键错误。这说明本次重启循环已被打断，不代表永久消除所有内存峰值。

此前维护暂停超时后，本地编排仍尝试下一条stop SSH属于流程缺陷；无远端停止成功回执，不能把未知状态写成停服成功。后续切换必须以明确成功回执串联，连接失败立即中止并核对实际状态。

### 仍存在的服务器问题及解决方案（本轮未修改代码）

| 问题与证据 | 后续最小修复及验收 |
| --- | --- |
| 部分`saveState`路径仍全量写约530MB快照，事务内TRUNCATE/COPY持排他锁；并非每条业务都全量写 | 合并检查点保存、审计剩余调用，逐项完成结构化增量持久化；保留兼容恢复及全部历史，不直接清数据。以真实大状态校验一致性、峰值和并发写入 |
| ready检查重复执行存储初始化并读取快照更新时间，遇到全量保存锁会阻塞 | 初始化移至启动阶段；ready采用轻量连通性检查并显式暴露持久化失败、积压和新鲜度，不能掩盖保存故障。覆盖锁等待/失败/恢复 |
| shutdown在关闭HTTP接入及清理所有保存定时器之前调用pool.end；旧日志已有pool关闭后写入与shutdown timeout | 先阻止新写入，撤销全部保存定时器，等待在途写入和保存队列，最终保存后再关闭pool；保持原控屏语义。覆盖并发请求、定时器与SIGTERM竞争 |
| 审计表约579万行、2.3GB，取最新5000条无时间索引；EXPLAIN显示并行全表扫描/排序，冷启动该查询约60秒 | 本地验证与ORDER BY DESC NULLS LAST匹配的索引及部署成本，生产另行授权迁移；逐步减小启动历史加载范围。不能在线盲建索引 |

本地隔离数据库复现三项：快照TRUNCATE使ready读取超过400ms并报57014；待执行保存定时器在模拟pool.end后仍写入并再次排队；5万条合成审计记录加匹配索引后计划从Seq Scan/Sort变为Index Scan。只修改并删除自建隔离schema，未改生产。证明文件见`LOCAL_PROOFS_20261026.jsonl`。这些是缺陷复现，不是已上线修复。

### 确认仍未闭环：搜索页退出失败，阻碍切号/探测

87、163在限制后重新准备，以及107准备过程中，仍发生`alipay_account_home_navigation_failed:search_activity_persisted`，约24–28秒后失败。原截图是普通搜索页和键盘，不是USB弹窗、账号列表或登录页。

确定的证据缺口是：XML执行路径回传日志被`lookup-recovery-trace`白名单过滤，缺少`exit_search_for_account_navigation`、`exact_search_back_button_unavailable`、`exit_search_via_exact_back_button`等步骤；保存的recoveryTrace为空。尚不能区分当时dump失败、未点击、点击后焦点未及时变化。约1GB Agent日志只做有界尾部读取，不能把未搜到当成动作没执行。

**修复顺序**：先补有界、脱敏的导航阶段/耗时/动作结果记录；基于新鲜页面确认键盘、返回元素、焦点，退出后验证首页，再进入原切号和测试账号探测；失败走短退避和受控重探，业务原ID继续跨机。先用三台真实失败XML/截图做整体路径回放，再用空闲单机验证，不盲目增加Back次数、不把普通导航失败判成设备故障、不扩展AI选择账号。

87/163的设备health.ready=true只表示池中健康资格，并非当前通道已探测就绪。107还存在accounts_cooling，115为本轮account_login_required，必须分开处理；不能把这些设备概括成“所有账号都正常”。
