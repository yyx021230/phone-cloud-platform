### 确认的代码缺陷与尚未确定项

rc.20启动恢复重新`am start -W`后只等0.7秒便要求当前焦点已是目标小红书用户，然后才进入通用的选择器处理循环。这会在合法Vivo选择器上提前失败，也会误拒绝尚未获得输入焦点的正常过渡。用本轮真实状态建立两项反例，未修改代码时均稳定复现相同的`foreground user does not match`异常；这是可重复的代码缺陷。

但本轮没有重现此前rc.20任务本身，也没有证明所有rc.18空根节点都来自同一底层原因。旧失败最终桌面/空根的事实保留，不把正常重跑或本地测试当作旧故障全部闭环。

### 最小修复

仅在已有的一次Vivo启动重试后，增加10秒轮询预算（最多20次，单次ADB另有8秒时限）：

- 只解析唯一物理display0和明确非安全、已关闭的锁屏状态。
- 正确用户的小红书前台可读元素；明确owner Vivo双开选择器交回原有元素选槽循环，再按app1/app2选择。
- 空焦点或桌面仅在关联Activity属于已知桌面/选择器/目标用户时等待，不反复发送启动、返回或唤醒指令。
- 错用户、陌生窗口、歧义/锁屏、超时停止；双开用户重新确认，元素读前后检查占用及窗口类型。
- 成功事件记录target/selector路径；失败说明pending、unproven、native read或窗口变化，避免所有失败只剩“槽位不匹配”。初次启动、采集列表/日期衔接、45秒加载和最多2次重入、共享服务与投屏不变。
