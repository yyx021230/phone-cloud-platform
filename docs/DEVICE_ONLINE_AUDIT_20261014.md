## 结论一：恢复批次重叠，动作等待时间可被绕过（已确认）

同一批123、140号出现以下顺序：

| 10月13日时间 | 事件 |
|---|---|
| 11:49:24.530 | 第一批开始，目标123、140 |
| 11:49:24.586/.587 | 两台各完成第1次 `restart_adb_interface`，日志均要求下一次检查等待30秒 |
| 11:49:28.930 | 第二批对相同两台开始，第一批尚未完成 |
| 11:49:29.205/.394 | 两台各完成第2次 `recreate_adb_root` |
| 11:49:29.612 | 第一批完成后验 |
| 11:49:34.425 | 第二批完成后验 |

两批相隔4.4秒，动作间约4.6～4.8秒，未遵守本次动作记录的30秒等待。109批中至少1对可直接关联到相同目标的重叠；不把该样本外推为所有批次都重叠。

实际生产源码 `src/index.mjs`：常规定时扫描和恢复唤醒经过 `runGuardedInterval("scan", ...)`，任务结束入口第1188行却直接调用 `scanAndSync`。恢复候选第4070行附近检查 `isPnpRecoveryTargetDue` 后，还要等待异步 Windows 安装器探测；第4133行起重新构建动作却不重新检查等待截止时间，第4383行附近拿到目标锁后仍不复核截止时间。目标锁在命令阶段结束即释放，而批次还会再等待5秒并做后验，故不能阻止另一次扫描用旧候选提前进入下一动作。

同窗存在 `post_task` 扫描和短信刷新任务，支持该入口可能参与重叠；日志没有贯穿扫描的ID，不能精确证明具体哪一任务触发了第二批。代码中的防重缺口和实际同目标提前恢复分别已有证据。

建议优先修复：所有入口共享同一扫描单实例执行约束；真正执行动作前，在目标互斥保护下复核最新 `inProgress/nextRetryAt`、拓扑和占用；后验完成前不得为同一目标开启新批次。保留D-024持续恢复，不扩大任何USB动作范围。

## 结论三：安装器探测失败被归入“驱动安装忙”（已确认）

137次批次延后都标记 `device_install_busy`，其中129次包含 `probe_failed`，其余8次记录真实安装器进程（共10条 `drvinst.exe` 进程记录）。129次不能作为Windows实际正在安装驱动的证据。

生产 `index.mjs:4850` 附近每次启动 PowerShell 全量 `Get-CimInstance Win32_Process` 后筛选安装器，整个命令预算10秒；异常统一返回 `busy:true` 和 `probe_failed`，丢失可直接统计的超时/退出码分类。本轮同类只读CIM查询本身耗时10.55秒，超过原命令预算，说明超时预算存在实际风险；但原日志错误信息截断，不能断言全部129次都是超时。本次也确实读到6个 `drvinst.exe`，因此不能把所有等待都当成误报。

建议：区分 `installer_busy` 与 `probe_unknown/timeout`，记录耗时、退出码、结果新鲜度；采用有界、较轻的探测并避免并发重复探测。未知状态仍不得盲目进行PnP变更，不能仅为恢复吞吐直接移除保护。
