# 支付宝查名字管理后台设计

## 当前采用：v4 简洁布局收尾

保持v3功能与一页结构，仅收尾交互：账号表有固定表头和明确滚动提示，不把页面无限拉长；筛选可一键清除；统计区分已知账号与尚未读取的手机；查询记录按最新时间排列。列表支持键盘滚动和焦点提示，仍为演示数据。真实账号状态、历史截图、采集与鉴权接口尚未接入，不改变查名调度或线上。

## v3 全部账号与失败截图（继续沿用）

延续v2一页简版，新增常驻的“全部手机与账号”，替换v2把完整名单放到详情的安排。不是只列本轮五台：名单中的每台手机都能找到，每个已知账号各占一行。完整后台仍为设计，未接生产。

| 手机 | 账号 | 账号状态 | 原因 | 什么时候恢复 | 失败截图 |
|---|---|---|---|---|---|
| 同一编号可有多个账号 | 脱敏标识、当前/历史/已保存 | 可查、受限冷却、需登录、待拼图、待探测、识别异常、未知 | 简短原因 | 冷却截止或恢复条件 | 查看截图 / 未留存 |

- 手机自身状态另显示在编号下方。一个账号受限不等于整台手机没有可用账号；保存账号、未记录限制也不等于已经就绪。
- 可按手机是否可查筛选，也可按账号状态筛选；支持手机编号/账号搜索、分页。未知账号列表仍保留该手机，显示“未读取、数量未知”，不伪装成零账号或可用。
- 冷却显示确切账号的开始/截止时间，点击详情可看；到期仍需重新探测。登录掉线标明本轮排除、下轮可探测。隔离与手机离线有独立原因，不重写为账号额度限制。
- 账号状态附采集时间、来源、当前身份确认时间；过期标待确认。全部账号是最近有效的已保存账号清单，不承诺知道手机上尚未读取的账号；库存名单、账号列表和状态分别显示完整性。
- 正式版名单及账号来自后台，不硬编码数量。本稿使用原表中48个已入库编号，148未入库；9台账号状态为演示，其他39台刻意展示未知。没有读取当前生产账号或宣称这就是线上可查数量。

### 失败截图

手机账号行、业务失败行和单条过程都有截图入口。打开的是**该次失败当时**的截图，显示手机、账号身份依据、失败原因、截图时间、轮次、原请求/内部尝试，不打开实时控屏。详情中的截图可继续放大，返回后保留筛选和分页。

设计稿仅实现图片查看弹层与信息对应，图片区域明确写“未接入真实截图”。缺图、截图采集失败、已过保留期、无权限分别显示；不能用当前画面或另一轮图片补成历史证据。账号身份未确认时写未知，不拿历史账号标签当确定归属。

正式开发优先复用已有失败证据；没有时才评估任务失败钩子中的有界采集，业务结束/转交不能被截图失败拖住，不为看图唤醒、点按手机或启动新ADB服务。截图跟随故障事件独立存储，用不可变evidenceId关联设备、原查询、尝试和时间；迟到上报不能替换别次证据。图片不嵌入全量JSON快照，不放公开静态目录，管理员鉴权后按需取缩略图/原图，做体积、保留期及访问审计约束。无真实失败截图的历史记录不能凭空补齐。

本轮只改原型、设计文档、主文档及预览，不实现采集/存储/API。验证覆盖全名单分页、账号筛选、多个账号、失败截图关联、缺图说明、窄屏；真正截图采集、权限、时效和生产准确性留待实现后验收。

## 1. 管理员进来先能回答什么

1. 本轮有没有启动、能不能接单、正在处理多少号码、还有多少排队？
2. 五个执行位置分别在查业务、探测、切号还是等待？为什么没有五台正常查？
3. 一个号码从提交到完成经历了什么？超时重提有没有重复执行？跨机交给了谁？
4. 哪台手机、哪个账号卡住了？是拼图、账号掉线、限制、页面不认识，还是设备离线？
5. 系统下一步是什么？等谁、等多久、满足什么条件恢复？是否需要管理员操作？
6. 卡片是刚刚采集的事实，还是旧状态？补丁已经在线生效，还是仅准备好了？

首页用结论和原因回答问题，技术ID与原始事件放详情。不能仅堆日志，也不能靠一个“查名字中”标签代表所有状态。

## 3. 运行总览：先解释容量，再看明细

### 3.1 顶部摘要

显示轮次ID、调用方、启动时间、首次接单门槛是否通过、当前是否接单、停止原因及停止阶段。首次两台门槛通过后，实时就绪不足两台不重新关闭已开放轮次；实际派单仍必须有合格手机。

统计分别展示：业务执行数、准备/探测数、等待人工数、排队数、近15分钟业务完成数。完成拆成“有姓名 / 明确无姓名”；另列失败与取消。**内部测试号码不计业务吞吐；重提不重复计数。** 历史统计按服务端定义的时间窗口与事件时间计算，不把截断列表当全量。

### 3.2 五个执行位置

每个位置显示手机编号、角色、当前步骤、持续时间、最近进展、下一步。角色至少区分业务、探测、切号准备、人工等待/接续、停止确认。等待人工是否释放位置以协调器事实为准；不靠前端重新推算锁。

旧离线任务的撤销隔离、待清理资源单独列出，显示所属旧尝试及撤销凭据，不能混入五个新执行位置，也不能把还未证实停止的任务藏掉。若预留数、执行数、任务锁对不上，显示“状态不一致待核对”，不给虚假正常结论。

### 3.3 为什么没有补满

按主阻塞原因互斥汇总，点击筛选对应设备；详情保留所有并存原因。优先级由后端统一定义并返回，前端不自行改变。展示候选数量、原机重探/切号进展、下次评估时间，以及“无合格候选 / 探测中 / 控屏占用 / 等停止确认”等调度实际理由。

不保证哪台未来一定接单，不用静态名单预测派发结果。展示最近一次派单决策：选择原因、候选被跳过原因、就绪证明时间、本轮业务分配量。管理员能检查是否平均分配，而不是只看到总次数；分别比较成功数、尝试数、忙碌时长，避免把多次重试当多笔业务。

历史样例：48启用中20失败隔离、10账号掉线、8全冷却、2离线、2退避、1控屏、5基础健康；5位置中1业务4准备。该样例说明为何“5位置占用”不等于“五台正在查客户号码”。20隔离不能解释为20台硬件损坏。

## 4. 轮次与号码：三个层级不能混淆

| 层级 | 标识与字段 | 用途 |
|---|---|---|
| 客户提交 | 调用方、提交时间、请求号/幂等标识、受理/复用/拒绝、关联lookupId | 说明客户两分钟超时换号重提为什么没有新增执行 |
| 统一业务请求 | lookupId、轮次、脱敏手机号、对外状态、内部步骤、排队时长、总期限、结果 | 一条号码业务的稳定主记录；成功一条返回一条 |
| 内部执行尝试 | attemptId、queryId、设备/账号、开始/结束、错误分类、停止确认/撤销、接续关系 | 解释同机恢复、切号、跨机和迟到回报 |

列表支持按轮次、调用方、状态、编号、时间筛选，按稳定游标服务端分页；完整号码搜索权限单独控制。详情默认显示可读时间线，技术事件按需展开。

时间线：外部提交 → 鉴权与防重 → 排队 → 就绪证明校验与派发 → 查询 → 人工/限制/掉线/识别异常分流 → 安全结束旧尝试 → 同原单接续 → 单条结果持久化 → 客户读取。每步含时间、来源、设备、原因和实际动作。未发生的步骤不能伪装成已执行。

“明确无姓名/未实名”是有业务证据的成功结果，值为空字符串。未知页面、掉线、超时、系统失败不是无姓名；后台分别显示且保留证据。客户端断开、两分钟超时也不等于服务端取消。重提命中规则与有效范围必须从实际服务返回，不能承诺无限期所有相同号码永远只查一次。

结束本轮详情显示：排队取消数、执行安全停止数、待确认/已撤销数、完成保留数、停止开始时间、下一次评估时间；自然15分钟空闲结束与开发者调用结束分别标明。新启动复用本轮、停止中拒绝、下轮重新开始也应记录，防止误认两次prepare启动了两套手机。

## 5. 设备与账号：资格必须有依据

设备列表显示：平台编号、所属Agent、是否在名单/启用、连接与心跳新鲜度、本轮角色、当前步骤、就绪资格时间、主阻塞、最近业务/探测时间、失败类别和次数、下一步及恢复条件。

设备详情分四块：

- **手机与任务**：Agent/连接/UI观察分别显示；轮次、预约、执行、控屏占用分别显示。在线不等于支付宝可用，就绪不等于一直有效。
- **账户账本**：脱敏账号、当前身份是否已确认、确认时间/来源、保存列表更新时间、限制事件、limitedAt/cooldownUntil、剩余时间、最后探测结果。历史缓存明确标“上次已确认”，不能冒充当前身份；未记录限制也不能标可查询。
- **失败和恢复**：页面不识别、身份不确定、账号掉线、额度限制、设备离线、执行器退出等分别记录。三次隔离显示三次证据及规则版本；页面错误不能被后台翻译成物理故障。
- **关联记录**：最近探测、客户号码、人工事件、账号切换、原单转交和管理员操作，均可跳转。

账号冷却到期只恢复重新探测资格，不能直接绿色就绪。账号掉线显示“本轮不分配；下轮重新探测”，与限制冷却、跨轮持久隔离分开。只读查看不会清失败次数、重置冷却或主动探测。

## 6. 人工处理与拼图后完整闭环

同一人工事件关联轮次、设备、账号身份、原查询/探测、challenge版本、观察时间、通知记录、执行复核。卡片状态与详情使用同一后端投影，不能各维护一套人工布尔值。

| 新鲜页面证据 | 管理台应显示 | 执行链路去向（需实际事件确认） |
|---|---|---|
| 仍有拼图 | 待人工，显示当前挑战与等待时长 | 保留原任务，按既有通知去重策略处理 |
| 拼图消失但用户仍控屏 | 页面已变化，等退出控屏/执行复核 | 不抢操作，不直接宣告就绪 |
| 当前账号限制 | 账户受限，等待/已保存冷却回执 | 原请求安全转交；原机切已保存可用账号并重探 |
| 账号登录失效 | 账号掉线，需授权登录 | 通知准确设备/脱敏账号，本轮排除，下轮可重探 |
| 原号码可信结果 | 正在读取原结果/已完成 | 保留原单，不重复输入；成功独立返回 |
| 已知正常页或可关闭弹窗 | 正在恢复查询/准备 | 按已验证兼容路径处理，不一律标拼图 |
| 加载、网络提示、未知页 | 正在有界复核/页面待兼容 | 展示期限和已尝试动作，不能当空姓名或无限等待 |
| 息屏、离线、Agent失联 | 观察不可用/设备异常 | 显示连接证据，沿用已批准恢复与隔离转交边界 |
| 轮次已停止、挑战或尝试已过期 | 历史人工事件已关闭 | 旧消息不重新点亮当前卡片，不接续已撤销尝试 |

上表包括尚未发布的post-human候选能力。正式开发按运行版本/Agent能力显示“已支持/未支持/证据不足”，不能单靠新界面声称线上闭环已修好。

通知分为待发送、失败待重试、机器人受理、事件已失效。机器人成功受理不能写“用户已读/已完成”，除非有真实回执。登录通知包含设备编号和可识别的脱敏账号；身份未确认明确写未知，不能借旧缓存指错账号。状态变化更新卡片，但不靠刷新页面发送群消息。

## 7. 新鲜度、准确性和刷新

每份数据含服务端生成时间、来源采集时间、接收时间、版本序号、完整性/错误。UI展示“采集→平台收到→页面显示”延迟，缺失就是未知。状态变化使用轮次/尝试/挑战和递增版本拒绝旧数据覆盖新状态。

拟定交互目标：可见页的当前摘要每2秒增量刷新、无重叠请求；后台标签页降频，恢复前台立即只读刷新；历史列表按需加载。收到新数据后一轮渲染即更新，同一版本卡片与详情一致。网络失败保留历史但显著标过期，禁止依赖过期状态执行管理动作；不把“现在刷新页面”当成“刚采集手机”。采集超时阈值遵守实际观察器能力和部署规则，不在前端擅自缩短。

必须测真实观察到展示的延迟分布及异常上界；2秒页面刷新不是2秒手机检测保证。观察器没有足够证据时，界面应显示待复核，不能以乐观更新提前标完成。读取失败、部分Agent缺失、时钟偏差及乱序事件均需显式呈现。

## 8. 数据接口与实现边界（设计，尚未新增）

| 拟新增GET资源 | 内容 |
|---|---|
| `/summary` | 当前轮次、明确口径的统计、执行位置、补位原因、版本与数据新鲜度 |
| `/rounds`、`/rounds/:id` | 分页历史和本轮结束/复用过程 |
| `/requests`、`/requests/:id`、`/requests/:id/events` | 业务分页、提交别名、尝试、结果和游标事件 |
| `/devices`、`/devices/:id` | 名单资格、账户账本、预约/任务/控屏与恢复信息 |
| `/incidents`、`/incidents/:id` | 人工/异常/通知去重关联、证据和处理结果 |

共同响应包含 `snapshotRevision`、`generatedAt`、`sourceObservedAt`、`partialErrors`；事件按不可变ID/序号分页，列表限制字段和最大页长。摘要计数在同一服务端快照计算；详情版本不同可显示“已更新”，不假装原子一致。无可靠下一步事件时写“等待协调器评估”，不在UI编造确定动作。

优先复用真实任务/账号/通知/审计来源，缺字段按最小范围补事件。业务状态仍由原协调器唯一写入，管理后台只是投影；不再建第二个调度器，不旁路数据库改状态。新增事件应有幂等ID、bounded保留/索引和体积预算，结合既有存储治理确定保存周期；不再无限增长单个完整JSON快照，不在本设计中擅自迁移或删除历史数据。

## 9. 管理操作与权限

第一阶段接真实**只读**视图，先解决看不清。第二阶段再逐项开放结束本轮、暂停单机新派发、申请单机重探、规则配置等已有业务能力的管理入口；原型均禁用。

所有动作需服务端管理员校验、预览影响、明确设备/轮次/请求范围、expectedRevision并发检查、幂等提交、审计和可查询执行结果。预览后状态变化重新拒绝或重新确认，不能过期弹窗照做。不开放“一键全部解禁”“重置冷却”“强制杀掉所有手机”等快捷操作；没有ADB重启/切身份、驱动或共享恢复入口。

查看后台和实际控屏是不同权限。只读查看证据不能隐式打开并占用实时控制；人工协作用户的窄权限也不等于管理员。对接系统API Key不能访问管理台，只显示调用方标识、权限范围、密钥尾部/更新时间，不返回密钥明文。

手机号、姓名、账号默认脱敏；查看完整值和证据附件需要明确权限、范围与审计，证据保留与导出规则沿用项目政策。日志中不保存真实密钥、登录凭据或未经筛选的敏感截图链接。越权测试直接请求管理API验证，不能只测试隐藏菜单。

## 10. 开发顺序与验收

1. 只读后端投影、字段口径与权限测试；接入总览、号码/手机详情。先本地模拟现有快照和历史事件。
2. 补齐缺失可观测事件，接人工/通知/版本与审计，验证乱序/失联/大数据分页。涉及Agent才按既有冻结、投屏回归和单独发布流程处理。
3. 只读灰度与真实页面对照，确认后再实现单项管理操作。管理员UI上线不能代替查名闭环补丁的发布与真机验收。

| 必验场景 | 验收依据 |
|---|---|
| 五位置仅两台查 | 其余每个位置角色、占用依据、下一步明确；统计可回溯 |
| 账号限制/登录/页面异常 | 三种原因不同，当前与缓存账号分开；不统称离线 |
| 人工完成后出现限制/登录/结果/未知 | 手机真实画面、事件、卡片一致；无旧挑战覆盖 |
| 20条排队，最多5台，后续手机就绪 | 未提前绑死队列；派单事件可解释补位与平均分配 |
| 两分钟换请求号重提 | 一个统一请求，多提交别名，实际尝试数不虚增 |
| 限制后跨机/设备离线 | 原lookupId不变，停止确认或有效撤销隔离有凭据，迟到结果不覆盖 |
| 停止过程中手机离线 | 正在停止的步骤/期限可见；已完成结果保留，下轮独立 |
| 账号冷却自然到期 | 倒计时归零只表示可重探；未探测不标就绪 |
| 页面/接口状态过期与乱序 | 旧值明显标识，管理动作不可基于过期值执行 |
| 部分Agent缺失/大历史量 | 摘要标部分失败；分页有界，不能浏览管理台拖慢业务 |
| 无姓名与系统失败 | 前者有明确证据、结果空字符串；后者保留错误，绝不伪装成功 |
| 未授权/非管理员/API Key | 管理API拒绝，任何接口不泄漏真实Key |

验收既需要本地模拟，也需要后续获得范围授权后的生产只读核对。不可宣称“完美无缺”。
