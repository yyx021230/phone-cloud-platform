## 4. P0：154号错误降级，已锁定到具体分支

154号本轮12条业务：0条姓名成功、1条未找到、11条失败；同期却有17次成功探测。11次失败中10次最终是task_failed，message为停止PocoService的am force-stop命令失败；另1次是lookup_old_worker_exit_unconfirmed。

10条独立任务的生产事件全部一致：operation=query、fallbackDriver=xml_uiautomator、reason=lookup_reader_cleanup_unconfirmed。结合匹配的生产源码，链路如下：

1. 查询开始前的Poco探活/重建遇到问题，读取器停止没有取得手机端清理证明。
2. restartLookupQueryOnce的保护列表识别cleanup_unconfirmed，拒绝重启查询。
3. shouldFallbackAlipayPocoFailure没有同样的保护项，仍允许XML兜底。
4. ensureXmlUiAutomatorReady以xml_uiautomator原因调用停止；该原因不属于lookupRecovery。若宿主worker已被移除，停止可直接返回true，未再要求Android absence证明。lookup stop barrier也会在操作结束时从内存移除，不能作为持续不确定状态的证明。
5. 接着执行停止PocoService的命令。10条均在这里失败，Agent度量约19.29—20.08秒。
6. 此准备步骤位于XML执行器的try外，异常退化到通用task_failed，原“清理未确认”的阶段和runnerReason丢失；云端最终记lookup_execution_failed。

这是已确认的控制流与诊断根因；它没有证明最初命令失灵由HANS、驱动、USB、授权或共享ADB server引起，也没有证据证明这10次发生了新号码重复输入。不能把阻止错误降级误称为修复手机底层传输。

相关位置：windows-agent/src/alipay-poco-fallback-policy.mjs、lookup-page-recovery.mjs，以及index.mjs的recycleAirtestWorker、stopAirtestWorker、taskAlipayNameLookup和ensureXmlUiAutomatorReady。仅把XML准备移进try会改善报错，不能修复证明降级。后续应统一“旧进程/手机端清理未确认”的禁止新驱动/新输入边界，覆盖message、code-only、包装前缀、worker_exit和forward清理失败，并保留原始cause及阶段。
