# CPS × 云手机平台：企微客户对接方案

版本：v0.6（联调候选）

文档更新：2026-11-09
依据：CPS提供的《CPS企微客户对接文档（对外版）》v1.0，2026-11-02。

**本稿用于本地联调，正式上线待确认。** 客户下发按`wecom_phone`指定执行账号，结果回传沿用CPS原协议；提供查询全部设备状态的接口。本文标注“建议／待确认”的内容，须双方确认后实施。

## 1. 三个接口

| 接口 | 调用方向 | 方法与路径 | 用途 |
|---|---|---|---|
| 客户下发 | CPS → 云手机平台 | `POST /api/v1/lead/dispatch` | CPS指定企微成员、传入客户号码；平台受理后异步执行 |
| 添加结果回传 | 云手机平台 → CPS | `POST /api/v1/lead/callback` | 平台通知CPS：申请已发送、已是好友或添加过频 |
| 查询全部设备状态（新增） | CPS → 云手机平台 | `POST /api/v1/lead/devices/query` | 查看全部设备的在线、占用、可用状态及已授权成员映射 |

查设备和下发客户共用一个平台基础地址，接口路径保持不变。正式对接当前按 HTTPS 约定，域名和证书待确认。若双方确认采用公网 HTTP，可沿用 `http://47.98.127.132` 作为平台基础地址。该地址的 CPS 路由尚未开放，待发布验收后切换。

结果回传由云手机平台向 CPS 发起。CPS 提供独立的正式 HTTPS 回调地址，路径为 `/api/v1/lead/callback`。

设备查询的`accounts[].wecom_name`返回平台配置的企微昵称，供显示选择；允许重名，不从手机页面读取，不用作执行账号身份。下发请求不需要也不接受`wecom_name`，仍按`wecom_phone`定位。

`wecom_phone`是执行账号的企微登录手机号，平台按绑定定位到手机和企微账号。`phone`是待添加的客户手机号。手机号路由的业务必填项为`lead_id`、`phone`、`wecom_phone`。

## 2. 完整业务流程

1. CPS查询设备状态，了解哪些企微成员当前可受理任务。
2. CPS下发`lead_id`、客户手机号`phone`、执行账号手机号`wecom_phone`及公共签名参数。
3. 平台校验签名、时间戳、防重记录和成员映射，确认能否受理。
4. 受理成功后立即返回，不等待手机操作；后台执行搜索、备注核验和添加。
5. 平台按真实结果回调CPS；回调失败只重试通知，不重新添加客户。
6. CPS收到`success`后，继续等待企微官方事件及客户身份匹配，确认客户是否真正通过。

设备列表只是即时快照，不预留手机。列表显示可用到正式下发之间若发生占用，平台仍会重新核对，不会抢占查名字、控屏或其他任务。

设备重新可用仅表示占用已经释放，不代表添加成功；CPS应以结果回调确认业务结果。普通异常也可能在清理确认后释放手机，不能根据设备变为空闲自行把线索标为已添加。

## 3. 公共通信与签名

沿用CPS原文：UTF-8 JSON，`Content-Type: application/json; charset=utf-8`，业务及签名字段放在JSON Body。新增设备查询也使用POST，以保持同一套Body签名规则；不使用GET请求体。

| 公共字段 | 类型 | 说明 |
|---|---|---|
| `app_id` | STRING | 双方约定的接入应用标识 |
| `timestamp` | INT64 | 毫秒时间戳，允许与服务端相差不超过5分钟 |
| `nonce` | STRING | 每次请求重新生成，5分钟内不得重复 |
| `sign` | STRING | SHA256结果，小写64位十六进制 |

签名步骤与原文一致：

1. 取Body顶层全部字段，排除`sign`、值为`null`和空字符串的字段。
2. 字段名按字典序升序排列，以`key=value`拼接，用`&`连接。
3. 末尾追加`&secret=密钥`，按UTF-8计算SHA256。

字符串不去除首尾空格、不做URL编码；`0`和`false`参与签名。密钥不放入Body，不向CPS提供平台管理员令牌。每次重试更新`timestamp`、`nonce`和`sign`，业务内容及原`lead_id`保持不变。

`lead_id`按原协议使用正INT64，须无损保存和原样回传。JavaScript不得先用普通Number解析19位ID再签名；平台内部按十进制字符串保存，对外仍序列化为原始整数。

## 4. 接口一：客户下发

### 4.1 地址及请求

`POST {平台基础地址}/api/v1/lead/dispatch`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `lead_id` | INT64 | 是 | 原线索ID；平台内部按`app_id + lead_id`防重 |
| `phone` | STRING | 是 | 客户11位大陆手机号；用于搜索和备注手机号核验 |
| `wecom_phone` | STRING | 是（本版） | 执行账号的企微登录手机号；可从设备列表`accounts[].wecom_phone`取得，参与签名 |
| `city_id` / `city_name` | STRING | 否 | CPS原城市字段 |
| `cmb_id` / `cmb_name` | STRING | 否 | CPS原品牌字段 |
| `cmd_id` / `cmd_name` | STRING | 否 | CPS原车系字段 |
| `app_id` / `timestamp` / `nonce` / `sign` | 按第3节 | 是 | 公共签名参数 |

```json
{
  "lead_id": 123456,
  "phone": "13800138000",
  "wecom_phone": "13900139000",
  "app_id": "cps_partner_demo",
  "timestamp": 1793584800000,
  "nonce": "demo_dispatch_001",
  "sign": "bcf66dc9973e1c59b7ad3f7b81a1c3b863985803afb602b980a20a9ef3f3184f"
}
```

本稿示例均为公开演示数据，签名使用CPS原文的`demo_secret_only_for_document`，仅用于离线核对。实际调用必须替换凭据、时间和随机串。

### 4.2 受理响应

受理成功和已受理的相同线索重发，均返回：

```json
{"result": null, "timestamp": 1793584800000, "success": true, "code": 200, "message": "已接收"}
```

当前不能受理时返回：

```json
{"result": null, "timestamp": 1793584800000, "success": false, "code": 2003, "message": "指定企微成员的设备正在被占用"}
```

成功响应仅表示任务已可靠保存，不代表好友申请已发送。签名、时间戳、nonce或请求错误按第8节处理；调用方同时判断Body中的`success`与`code`，不能只看HTTP状态。

### 4.3 防重及账号规则

`phone` 接受符合格式的大陆手机号，客户号码无需逐个加入白名单。`wecom_phone` 须是平台已授权并核验绑定的执行账号。每次下发仍须通过签名和防重校验。

- 同一线索、相同业务内容重复下发，返回原受理结果，不重复搜索、修改备注或发送邀请。
- 同一线索更改手机号、企微成员或其他已受理业务参数，拒绝覆盖原任务，保留原记录供核对。
- 已受理任务不会因为重启、CPS超时、更换nonce或回调失败而变成一次新的添加。
- 平台按执行账号手机号记录防重和限频。同一设备槽位对同一客户已有发送记录或发送结果待确认时，更换 `lead_id` 也不会再次发送。是否已是好友由企微结果确认。
- 按一机一企微配置。`wecom_phone` 唯一对应一台手机的主号（`main`）。账号未登记、绑定冲突或未核验时，平台拒绝受理。
- CPS 从设备查询中取得 `wecom_phone`，平台按内部绑定确定执行手机。更换登录账号时，平台先停用旧绑定并确认新绑定。
- 手机离线、占用、映射缺失或未核验、执行器未就绪时，不承诺受理。已受理后再遇异常，则跟踪原任务，不让CPS重复添加。

### 4.4 备注规则

**备注名只使用完整的`lead_id`十进制文本**，例如`lead_id=123456`时，备注名为`123456`；不拼接手机号或下划线。此规则按2026-11-04最新要求替换此前的`手机号_线索ID`格式。

**备注名最多20个字符**（当前平台按Unicode码点计数）。协议允许的正INT64最多19位，均可完整用作备注名；例如`9223372036854775807`原样保留，不截断、不转成浮点数。调用方也必须以无损INT64方式构造JSON数值并签名，避免语言默认数值类型造成精度损失。

描述为空时写入`leadId:完整线索ID`，例如`leadId:123456`；已有非空描述沿用现有保护策略保留，不覆盖已有客户资料。当前线索匹配以备注名中的完整`lead_id`为准，不能把保留的旧描述当成本次线索ID。CPS开发应按备注名完整线索ID对齐官方事件匹配；本文规则更新不代表双方正式联调已完成。

**备注手机号必须单独核验。** 将客户号码写在备注名或描述中，不能替代备注手机号字段。字段已经正确填写时应确认现值；缺失、不同或页面无法确认时，停止在发送前，不能假报设置成功。

## 5. 接口二：添加结果回传

### 5.1 地址及请求

`POST https://{CPS域名}/api/v1/lead/callback`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `lead_id` | INT64 | 是 | 原下发ID，原样回传 |
| `result` | STRING | 是 | 仅使用下表三个小写值 |
| `phone` | STRING | 否 | 原客户手机号；补充信息，不替代企微内真实备注 |
| `wechat_nickname` | STRING | 否 | 客户微信昵称；仅在有真实结果时填写 |
| `remark_phone_set` | BOOLEAN | 否 | 仅在独立字段已核验时填写true，不以备注名推断 |
| `fail_reason` | STRING | 条件必填 | `failed`时须符合CPS现有接收条件 |
| `app_id` / `timestamp` / `nonce` / `sign` | 按第3节 | 是 | 公共签名参数 |

| `result` | 平台回传条件 | CPS按原文处理 |
|---|---|---|
| `success` | 有明确证据确认好友申请已提交；不是仅点击了发送 | 等待官方事件，不直接认定客户已通过 |
| `duplicate` | 确认指定企业、成员与该客户已经是好友 | 将线索建联状态更新为已添加 |
| `failed` | 确认本次遇到添加好友过于频繁 | 暂停该成员当日自动分配，线索建联状态不变 |

`failed`的`fail_reason`必须包含`添加好友过于频繁`或独立错误码`code=224`。`code=2240`、普通网络错误、账号离线、客户搜索不到都不属于该结果。

申请已发出的回传示例

```json
{
  "lead_id": 123456,
  "result": "success",
  "remark_phone_set": true,
  "app_id": "cps_partner_demo",
  "timestamp": 1793584800000,
  "nonce": "demo_success_001",
  "sign": "a032c5c3a0756b7b723f3795e2d616e66d0c0aa99db531a12eb6768a687d6591"
}
```

添加过频的回传示例

```json
{
  "lead_id": 123456,
  "result": "failed",
  "fail_reason": "添加好友过于频繁",
  "app_id": "cps_partner_demo",
  "timestamp": 1793584800000,
  "nonce": "demo_failed_001",
  "sign": "417e2b0b54e9feb727a6bbb040e4ed2d6072100b191146c145fab2b87c18b8cf"
}
```

### 5.2 确认与重试

CPS 返回 HTTP 2xx，且响应体包含 `success: true` 和 `code: 200`，平台才将通知记为完成。

- 网络中断、响应未确认或服务端500：保留同一线索和结果，只重试回调。
- 每次回调重试使用新的nonce、时间戳和签名，绝不重跑手机添加流程。
- 建议最多5次尝试（含首次），重试间隔5、10、20、40秒；具体参数需双方确认，不是CPS原有下发重试机制。
- 签名、参数、线索不存在等错误：停止盲目重试，保留错误并处理原因。
- 回调结果和发送记录持久保存，服务重启后仍能对账，不清除原发送防重凭据。

## 6. 接口三：查询全部设备状态（本方新增设计）

### 6.1 地址及请求

`POST {平台基础地址}/api/v1/lead/devices/query`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `online_only` | BOOLEAN | 否 | 默认false，返回全部设备，包括离线、未映射和占用设备；true只筛选在线 |
| `app_id` / `timestamp` / `nonce` / `sign` | 按第3节 | 是 | 与客户下发使用相同签名规则，查询也不能重复使用nonce |

全量设备可见权限由平台授予 CPS 接入应用。账户信息仅返回该接入方获授权的成员映射。

```json
{
  "online_only": false,
  "app_id": "cps_partner_demo",
  "timestamp": 1793584800000,
  "nonce": "demo_devices_001",
  "sign": "5683b95e48b44a2f45e3d8a0aab647e7e90569e3919c769b8b2097eeaea48457"
}
```

### 6.2 响应示例

```json
{

  "code": 200,
  "message": "查询成功",
  "result": {
    "devices": [{
      "device_number": "200",
      "device_name": "200",
      "online": true,
      "adb_online": true,
      "agent_online": true,
      "listed": true,
      "busy": false,
      "busy_reason": "",
      "occupancy": null,
      "available": true,
      "unavailable_reason": "",
      "accounts": [{
        "wecom_phone": "13900139000",
        "wecom_name": "示例昵称",
        "app_slot": "main",
        "binding_verified": true,
        "enabled": true,
        "available": true,
        "unavailable_reason": ""
      }],
      "last_seen_at": null,

    "capacity": {"limit": 2, "active": 0, "remaining": 2}

```

示例中的设备数量、并发容量和时间均为演示，不是生产固定值。`capacity`取平台当前配置和运行状态，不因本次对接提高并发。

### 6.3 字段语义

| 字段 | 说明 |
|---|---|
| `device_number` / `device_name` | 平台实际手机编号和展示名；无法确认编号时number可为null，不伪造编号 |
| `online` | 平台当前判定手机在线；不等于企微已登录或一定能添加成功 |
| `adb_online` / `agent_online` | 手机通道与Windows执行端的心跳状态 |
| `listed` | 是否在平台上架；下架手机不能新接任务 |
| `busy` / `busy_reason` | 物理手机是否被占用及原因，包括查名字、控屏、其他企微任务等 |
| `occupancy` | 仅含占用类型和中文说明；无占用为null，不包含占用人或客户信息 |
| `available` | 该手机至少有一个已授权、已核验成员满足当前单机调度条件；仍须结合全局capacity，不是预约或执行成功保证 |
| `unavailable_reason` | 不可用的机器可读原因，见下表 |
| `accounts` | 新接入每台手机仅配置一个企微账号；已核验映射为一项，没有映射时为空数组。保留数组结构兼容原接口 |
| `accounts[].wecom_phone` | 对应手机唯一企微登录手机号，原样用于下发请求；不返回装卡手机号 |
| `accounts[].wecom_name` | STRING或null，平台配置的企微昵称（如“小文”），不是实名人或手机展示名；缺少配置返回null。允许重名，不能按昵称路由或反查官方身份；只读字段，不回传到下发接口 |
| `accounts[].app_slot` | 本轮新名单统一为main；不要求CPS选择分身。旧版本clone语义仅作兼容保留，不启用新双开映射 |
| `accounts[].available` | 该手机的企微成员当前是否可受理；仍受手机占用和全局容量约束 |
| `accounts[].unavailable_reason` | 该具体成员不可用的原因，例如成员添加频繁；不同成员的状态分别记录 |
| `accounts[].binding_verified` | 平台管理方是否已确认此手机号与手机绑定；本轮可依据用户已确认的新表登记，在线状态本身不等于绑定确认 |
| `last_seen_at` / `adb_last_seen_at` | 原始心跳／通道状态上报时间，未知为null |
| `updated_at` | 本次列表生成时间，不能当作每台设备的新心跳 |
| `capacity.remaining` | 平台当前还可受理的企微执行名额，0时应等待 |

建议每5秒查询一次。接口只读取平台已有状态，不触发手机扫描、安装、恢复、启动企微或账号切换；签名防重账本的写入不改变设备和业务任务。

仅返回该CPS接入方获授权的企微登录手机号，不额外返回装卡手机号、ADB序列号、管理员令牌、任务所有人或其他客户资料。

### 6.4 不可用原因

| `unavailable_reason`示例 | 含义 |
|---|---|
| `member_not_configured` | 未配置或未授权企微成员映射；手机在线也不能执行 |
| `member_binding_unverified` | 绑定未核验或成员未启用 |
| `device_not_listed` | 手机未上架 |
| `adb_offline` / `agent_offline` | 手机连接或执行端不在线 |
| `device_busy` | 被查名字、控屏或其他任务占用 |
| `member_rate_limited` | 对应企微成员已确认添加过频，暂不接新任务 |
| `device_number_conflict` | 手机编号映射冲突，需要平台处理 |
| `wecom_not_configured` | 不在当前已验证、已启用的企微范围 |
| `remark_phone_protocol_not_ready` | 执行器尚不支持所需的备注手机号核验 |

上述错误字段是本方新增接口的设计；不代表CPS原回调已经支持这些失败原因。

## 7. 平台内部保障

- **精确账号绑定：** 企微登录手机号`wecom_phone` → 唯一手机编号＋main。映射缺失、冲突或未核验时拒绝新任务。
- **物理手机互斥：** 同一手机的主号和分身不能同时操作；查名字、控屏和企微任务共用排他占用。不同空闲手机可独立执行。
- **持久防重：** 线索、原任务、发送尝试和结果通知分别记账；响应丢失先查原记录，不能创建第二次发送。
- **结果不明保护：** 点击超时、账号状态变化、备注保存或发送结果未确认时，不盲目重放，不改用另一个企微成员。
- **执行与回传分离：** 手机添加完成后，通知失败不会重新占用手机执行添加。
- **限制隔离：** 确认添加过频后，立即暂停原成员的新任务，不等回调成功后才生效；不自动换其他成员替这条线索执行。同机另一个成员不继承此限频状态，但仍共用手机互斥。其他空闲手机独立推进，不触发全局手机恢复。

## 8. 错误响应和非频繁失败

沿用CPS错误码：`200`成功，`1001`签名错误，`1002`时间戳过期，`1003`nonce重复，`2001`线索不存在，`2003`参数或请求不符合要求，`500`内部错误。

平台在受理前发现映射缺失、设备占用、离线或未就绪，返回`success=false`、`code=2003`及具体原因。已经受理的任务若执行中出错，须保留原线索和真实错误。

**原协议存在一个必须对齐的缺口：CPS当前不接收“登录失效、需要人工验证、手机号搜索不到、连接异常、结果不明”等普通执行失败。** 平台不会把它们伪报为“添加好友过于频繁”，也不会伪报成功。这些情况先留在平台原任务和异常处理记录中；CPS不能据此认定任务已完成。

**建议双方扩展现有结果回传对普通失败的处理，无需增加第4个接口。** 具体结果值／错误字段由CPS确认；确认前仍严格只回传原文允许的三类结果，不发送CPS当前会拒绝的泛化`failed`。

本地执行还须区分：RPC通信失败、客户搜索等待超时、系统面板遮挡。`system_overlay_interrupted`表示通知栏／快捷设置覆盖企微，停止操作、不自动关面板，也不触发拼图逻辑；网络不佳导致搜索迟迟没有结果，不等同于Poco读取失败。上述异常均不回传为成功或添加过频。内部读取连接复用不改变三个外部接口、签名、字段或重试规则。若已实际显示“查找中”后连续三帧返回同一号码的搜索框及网络查找行，停止并记录`wecom_search_returned_without_result`；这不等于客户不存在，也不单独证明网络或Poco故障。不得因此补点搜索、保存或发送；短暂两帧过渡和没有出现查找中的初始搜索页不触发该判定。

## 10. 联调验收清单

| 场景 | 预期 |
|---|---|
| 原文签名样例、中文、空值、0／false和最大INT64 | 签名一致、ID无损 |

| 同线索重复下发、超时丢受理应答、服务重启 | 仍只有一条添加任务 |
