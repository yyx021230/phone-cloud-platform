# Phone Cloud 大版本候选验收单

候选范围：D-015、D-017、D-019、D-021。四项作为同一个 releaseId 发布、同一个维护窗口验收、同一个整体回滚，不拆成多个线上版本。实时投屏与控制继续遵守 D-001，不在本版本修改。

## 一、发布前硬门槛

- `npm run test:big-release` 必须全部通过。
- 小红书账号迁移必须达到：全部已配置槽位覆盖、`unresolved=0`、`ambiguous=0`、`duplicateIds=0`；跨设备唯一别名匹配必须在报告中单独列出。
- 短信迁移预检必须输出 `invalid_business_keys=0`，并保存总行数、逻辑行数、重复组和待归档行数。
- 必须准备 PostgreSQL 全库备份、当前服务端镜像、Windows Agent 目录备份、当前设备账号 JSON 备份。
- 维护窗口开始前必须确认没有投屏会话、扫码任务、短信等待任务或 Windows DeviceInstall/PnP 动作。
- D-021 必须先在隔离 Windows 或明确维护窗口完成真实 PnP 目标测试；生产用户使用期间不得用线上手机补该测试。

任一门槛不满足，整个大版本不得发布。

## 二、同一维护窗口内的原子顺序

1. 关闭新任务入口，等待现有任务退出。
2. 停止 Windows Agent 和云端应用写入，保留 PostgreSQL/Redis。
3. 完成四类备份并记录校验值。
4. 执行小红书 ID 迁移，立即校验全部槽位。
5. 执行 `deploy/sql/20260817-big-release-sms-message-key.sql`：先归档重复短信，再建立 `(device_id, message_key)` 唯一索引。
6. 部署同一个 releaseId 的云端服务、静态资源和 Windows Agent。
7. Windows 通知补全必须显式配置作用域：指定序列号白名单，或显式设置 `smsNotificationFallbackAllDevices=true`；仅打开总开关但未配置作用域时保持零设备启用并上报告警。
8. 先启动云端并完成数据库烟雾测试，再启动 Windows Agent。
9. 完成第三节全部验收后恢复任务入口。

## 三、上线前统一测试矩阵

### 小红书稳定 ID

- 当前139个已配置槽位必须迁移139个。
- 账号改名后，设备绑定和历史任务仍按 `xhsId` 对应。
- 相同 `xhsId` 不能跨手机或跨同机双槽重复绑定。
- 当前已确认一项跨设备移动：表格145号“驰电车讯”对应生产185号，必须在迁移报告中保留审计标记。

### 短信全量刷新和通知补全

- 用户主动刷新必须执行 Provider 全量对账，后台同步继续增量。
- `dumpsys isub` 的订阅映射优先于旧平台卡槽缓存。
- Provider、通知两源相同短信只保留一条；Provider 后到时补齐 `_id`、卡槽等权威字段且平台 `messageId` 不变。
- ColorOS 将通知正文和发件人压缩时，只有同设备、跨源、30 秒内且双方都只有一个相同验证码的记录才能按最近时间合并；不同验证码、多验证码或同源 Provider 行必须保持独立。
- 通知白名单为空且未显式全量时，一台设备也不能运行通知采集。
- 无活动短信通知时不发送空批次写请求。
- 通知补全先只对白名单设备启用；152号首条 notification-only 样本必须进入平台后才继续灰度。累计至少10条真实验证码且10/10进入平台、无重复、无正文日志泄露后，才允许显式开启全设备作用域。

当前上线前真实样本进度：54号、152号已观察3条。前两条同时进入 Provider 与 ColorOS 压缩通知，候选正式解析器成功；第三条152号样本只出现在通知、约1.12秒捕获，公开 Provider 在十分钟后仍无新增，直接证明通知兜底必要。生产通知补全仍未开启，因此第三条没有写入生产库；它将在152白名单上线后作为首个端到端验收目标。

已知数据差异：用户提供的 `18627591004`、`15608456692` 反查后均属于152号而非154号；17:22短信实际是152号 Provider `sms:148`、`sub_id=2`。手机实时映射为 `sub_id=1 → SIM1`、`sub_id=2 → SIM2`，生产平台152号保存的号码卡槽与手机展示相反。用户明确决定本次不修改号码数据，因此它不是发布写入项；短信所属卡槽必须继续以D-015实时 `dumpsys isub` 为准，不能由管理员号码数组推断。

恢复队列不得作为全局短信门禁：异常手机只影响自己的同步，其他 ADB 在线手机必须继续执行 Provider 与通知补全。真正开始 PnP 动作前仍使用现有抢占机制中止在途后台短信命令，避免 Windows DeviceInstall 与 ADB 读取竞争。

### 恢复安全

- 正在投屏或执行任务的手机不进入 PnP 动作候选，但其掉线必须进入熔断观测。
- 每批真实 PnP 动作结束后持续观察180秒；窗口跨 Agent 重启持久化。
- 观察期内允许目标 ADB reconnect，不允许开始下一批 PnP 变更。
- 任一非目标在线手机掉线立即打开熔断并保留连带证据；后续命令失败不得覆盖已有名单。

### 平台回归

- 登录、设备列表、普通用户占用显示、短信库、扫码任务、图片导入和实时投屏基础流程全部通过。
- 云端 `/readyz`、PostgreSQL、Redis、Windows Agent 心跳正常。
- releaseId、服务端镜像和 Windows Agent 文件哈希与候选清单一致。

## 四、整体回滚

任一核心验收失败时，不做局部热修，整体回滚：

1. 再次关闭任务入口并停止云端与 Windows Agent 写入。
2. 恢复上一版云端镜像、静态资源和 Windows Agent 目录。
3. 执行 `deploy/sql/20260817-big-release-sms-message-key-rollback.sql`，移除业务唯一索引并恢复本版本归档的重复行；如迁移执行中异常，优先恢复发布前全库备份。
4. 恢复发布前设备账号 JSON，撤销 `xhsId` 迁移。
5. 启动旧版云端和 Agent，验证设备数、任务队列、短信库与投屏基线后再开放入口。

归档表不得随回滚删除，直到大版本稳定观察期结束并完成独立备份。
