## 3. 为什么过去一直补而仍复发

1. **修复层级被混用。** 分类修正、恢复成功、解除隔离、扩大容量各自有效；但都不能替代初始故障消除及异常后的自动收尾。版本总结必须说明修到哪层。
2. **退出/恢复是跨层协议，过去逐个入口补。** Python、Agent调用方、错误包装、云端adapter、调度预约必须对“清理未确认”保持一致；某个函数返回false而上层照常继续，局部测试通过仍会失败。本次终审已实际发现并补齐多个调用入口，说明必须按调用图审查。
3. **安全性有约束，活性没有闭环。** 无proof不释放是必要保护；但retry2后永远return，保护了不重叠执行，却使设备和名额长期卡住。正确修复必须同时证明不误放、不无限占位，不能简单清锁或无限重试。
4. **旧失败有记录，却没有固定关闭条件。** 10/27已留下pidof失败；后续恢复或新版本测试数容易盖住未验项。该项应始终打开，直到对应失败链有正反证，而不是另换描述重新宣称修复。
5. **隔离测试适配器省略了生产时序。** 原生OCR、账户列表和截图成功，只证明这一步；共享Agent生命周期、主循环、结果回报和持久状态未被该测试证明。增加正常号码数量不能补齐这个缺口。

1. **上版核销**：逐项列L编号、上版实际发布的文件hash、当时通过路径、上版未验项、上线后是否有同类复发。未部署补丁不能算线上回归；不同错误表现不自动当新问题。
2. **本版范围**：明确修根因、恢复、分类还是诊断；每项列未解决部分。没有解决的L编号保留，不用新版本号重置。
3. **证明闭环**：失败原例、旧版反例、新版完整路径、异常组合、重复/取消/迟到、清理和后续任务证据；缺项则状态停在本地候选/待验收。
4. **上线复核**：实际部署hash、相同条件观察窗口及分母、同类错误复发、吞吐和结果正确性。没有复发仅是该窗口未观察到，不能声称永久无错。
